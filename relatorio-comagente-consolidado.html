2.5 Migração da Evolution API: VPS local → Supabase + Cloudflare R2 (11/08/2026)

A infraestrutura da Evolution API foi migrada completamente do servidor local (VPS) para a nuvem, seguindo o plano de migração em 4 fases.

ComponenteAntes (VPS local)Depois (nuvem)Status
Banco de dados PostgreSQL local na VPS — inacessível pelo Vercel Supabase PostgreSQL — acessível pelo Vercel e pela VPS ✅ Migrado
Armazenamento de mídia Base64 dentro do banco (imagens, áudio, vídeo) Cloudflare R2 — mídia nova vai direto para o R2 ✅ Configurado e testado

Variável de ambiente: EVOLUTION_DB_URL → Supabase session pooler (porta 6543). O ComAgente usa esse banco para: (1) mapeamento @lid → phone via getLidMapping() e (2) tabela _comagente_notify para notificações SSE em tempo real.

Pendências da migração ainda em aberto:

  • Fase 3 — Limpeza da mídia histórica: base64 antigo ainda está no banco Supabase. Precisa ser extraído para o R2 e removido do banco para liberar storage.
  • Fase 4 — Operação contínua: monitoramento (dashboards Supabase + R2), política de lifecycle no R2, backup dual configurado.
⚠ SSL obrigatório após a migração para a nuvem:

O banco local (VPS) não exigia SSL. O Neon exige. O arquivo lib/evolution/db-client.ts deve ter ssl: { rejectUnauthorized: false } — sem isso, todas as conexões falham silenciosamente e o sistema para de funcionar. Ver bugs 6.80 e 6.81.

const pool = new Pool({
  connectionString: process.env.EVOLUTION_DB_URL,
  ssl: { rejectUnauthorized: false },  // ← obrigatório para banco em nuvem
})
⚠ Nunca inserir na tabela Message sem o campo remoteJidAlt:

Um INSERT manual sem remoteJidAlt no JSONB key bloqueia o INSERT completo da Evolution API via ON CONFLICT DO NOTHING, corrompendo o mapeamento @lid. Ver bug 6.80.

Auto-provisionamento ao criar empresa

Em app/api/tenants/route.ts (POST), ao cadastrar nova empresa:

await execute(`SELECT create_tenant_schema($1)`, [d.supabaseSchema])
await execute(`INSERT INTO ${d.supabaseSchema}.instancia (empresa) VALUES ($1) ON CONFLICT DO NOTHING`, [d.name])

Schema criado, 14 tabelas provisionadas e instancia populada automaticamente. Falhas ignoradas (schema pode já existir).

6.22 Mensagens recebidas não apareciam no workspace — fix definitivo — 29/05/2026

Histórico: em 20/04/2026 foi implementada a busca via PostgreSQL da Evolution API para contornar o bug do endpoint HTTP que retornava apenas fromMe: true. Funcionou até ~26/04/2026.

Erro: mensagens dos clientes apareciam no preview da lista de contatos (via chat list HTTP) mas não dentro do chat (via query PostgreSQL). Testes diretos na Evolution API revelaram a causa raiz:

Tipokey.remoteJidkey.remoteJidAlt
Enviada (bot/IA)557182608738@s.whatsapp.net—
Recebida (cliente)211132707020926@lid557182608738@s.whatsapp.net

O WhatsApp moderno usa JID no formato @lid (device-linked ID) como identificador primário para mensagens recebidas. O telefone real fica em remoteJidAlt. A query PostgreSQL buscava apenas por remoteJid, nunca encontrando as mensagens recebidas.

Diagnóstico — testes diretos na Evolution API (29/05/2026):

Query HTTP enviadaResultado

where: { key: { remoteJidAlt: "phone@s.whatsapp.net" } }112 mensagens recebidas ✓

Solução implementada em app/api/evolution/messages/route.ts e lib/evolution/client.ts:

  • Eliminada dependência do PostgreSQL para busca de mensagens (instável)
  • Duas queries HTTP em paralelo via Promise.all:
    1. findMessages(phoneJid) → filtra por remoteJid = @s.whatsapp.net → mensagens enviadas
    2. findReceivedMessages(phoneJid) → filtra por remoteJidAlt = @s.whatsapp.net → mensagens recebidas
  • Merge deduplicado por key.id (WhatsApp message ID)
  • Horário corrigido de America/Bahia para America/Sao_Paulo

Análise: Inicialmente catalogada como vulnerabilidade média, a investigação do código revelou que lib/sheets/client.ts usa valueInputOption: 'RAW' em todas as operações de escrita (appendRows e updateRange).

6.80 a 6.82 — Bug: mensagens recebidas não apareciam no chat aberto — 16-17/08/2026

BUG SUPABASE Após a migração da Evolution API para o Supabase (session pooler), mensagens recebidas chegavam no histórico lateral mas não atualizavam o chat aberto. O usuário precisava sair e entrar no chat para ver a mensagem.

6.80 BUG saveReceivedMessage bloqueava save completo da Evolution API

Causa: Com SSL ativo no db-client.ts, o saveReceivedMessage no webhook passou a funcionar e gravava a mensagem sem o campo remoteJidAlt no JSONB key. O ON CONFLICT DO NOTHING bloqueava o save subsequente da Evolution API (que incluiria o remoteJidAlt). Resultado: getLidMapping() retornava mapa vazio → lidJid sempre null → query 3 (findMessages(lidJid)) nunca executava → mensagem não encontrada.

Correção: Removido o bloco saveReceivedMessage do webhook. Com SSL configurado, a Evolution API já persiste corretamente no Supabase com remoteJidAlt preenchido. O save manual era redundante e destrutivo.

Arquivo: app/api/evolution/webhook/route.ts | Commit: 92862d6

6.81 BUG Callback SSE usava lidJid stale — chat não atualizava

Causa: O callback do SSE chamava fetchMessages(selectedRef.current.telefone, selectedRef.current.lidJid) em paralelo com fetchChats(). O lidJid atualizado que o fetchChats traria nunca chegava ao fetchMessages. Além disso, havia race condition: o SSE disparava antes da Evolution API confirmar a mensagem no Supabase (latência do session pooler).

Correção: Callback SSE reescrito para sequenciar: (1) aguarda retorno do fetchChats, (2) extrai lidJid atualizado do contato aberto, (3) aguarda 500ms para a Evolution API confirmar no Supabase, (4) chama fetchMessages com o lidJid correto.

Arquivo: app/(app)/workspace/page.tsx | Commit: 92862d6

6.82 BUG Webhook crashava em MESSAGES_UPSERT + CHATS_UPDATE não tratado

Causa 1: A Evolution API envia o payload de MESSAGES_UPSERT ora como { messages: [...] } ora como array direto. O acesso messages[0] sem guard quebrava com TypeError: Cannot read properties of undefined (reading '0'), impedindo o pushNotification de disparar e quebrando todo o fluxo SSE.

Causa 2: A Evolution API envia CHATS_UPDATE (e não MESSAGES_UPSERT) na chegada de mensagens recebidas. Esse evento caía no default do switch e pushNotification nunca era chamado.

Correção: (1) Normalização do payload: Array.isArray(raw) ? raw : (raw.messages ?? []) com guard if (!messages.length) break. (2) Adicionado handler para CHATS_UPDATE e CHATS_UPSERT que extrai o JID do chat atualizado e chama pushNotification.

Arquivo: app/api/evolution/webhook/route.ts | Commits: b5f83c5, 6b10abe

Resultado: Mensagens recebidas aparecem automaticamente no chat aberto em tempo real, sem necessidade de sair e reentrar na conversa. Verificado via SSE EventStream no DevTools e código de monitoramento no console do browser.

6.83 Migração Evolution API: VPS local → Supabase + Cloudflare R2 — Documentação Completa (11/08/2026)

MIGRAÇÃO SUPABASE R2 Documentação completa da migração da Evolution API de servidor local (VPS) para nuvem: banco para Supabase PostgreSQL e mídias para Cloudflare R2, incluindo os bugs gerados e as lições aprendidas.

Contexto da migração

Até 11/08/2026, a Evolution API rodava com PostgreSQL local na VPS (agenciadia_evolution-api-db:5432) e armazenava mídias (imagens, áudio, vídeo) como base64 diretamente no banco. Esse banco era inacessível pelo Vercel (rede Docker interna). A migração para Supabase tornou o banco acessível de qualquer origem, e o Cloudflare R2 passou a receber todas as mídias novas — parando o crescimento acelerado do banco.

Como diagnosticar problemas similares no futuro

  1. Mensagens não aparecem no chat aberto → Verificar se db-client.ts tem ssl: { rejectUnauthorized: false }. Sem SSL, getLidMapping() retorna mapa vazio e todos os lidJid ficam null.
  2. SSE não dispara new_message → Verificar nos Vercel Logs qual evento o webhook está recebendo. Se for CHATS_UPDATE sem log de pushNotification, o handler não está tratando esse evento.
  3. Webhook crashando em silêncio → No Vercel Logs, buscar [Webhook] Erro não tratado. O webhook retorna 200 mesmo quando crasha internamente (fire-and-forget). Verificar se o payload tem a estrutura esperada.
  4. Race condition pós-migração → Se mensagens aparecem às vezes mas não sempre: aumentar o delay no callback SSE (atualmente 500ms). A latência do Neon pode variar.
  5. getLidMapping retornando vazio → Confirmar que as mensagens recebidas no banco têm key->>'remoteJidAlt' preenchido. Se estiver vazio, algum processo está inserindo mensagens sem esse campo e bloqueando o insert da Evolution API.
