2. Arquitetura do Sistema

2.1 Fluxo de Mensagens

WhatsApp → Evolution API → n8n (webhook: MESSAGES_UPSERT)

O ComAgente NÃO intercepta o webhook. Lê mensagens diretamente do PostgreSQL da Evolution API via polling. O n8n continua recebendo tudo normalmente.

2.2 Modelo Multi-tenant

Cada cliente (tenant) tem sua própria planilha Google Sheets como banco de dados isolado. O tenantId de cada usuário é o próprio ID da planilha.

6.23 Read receipt (✓✓ azul) para o cliente — 29/05/2026

Mensagens enviadas pelos clientes para o bot apareciam com apenas ✓ (enviado ao servidor) no WhatsApp do cliente — nunca evoluíam para ✓✓ cinza (entregue) nem ✓✓ azul (lido).

Causa: configurações da instância lucenadecoracoes no Evolution API tinham readMessages: false e readStatus: false. Com readStatus: false, a Evolution API bloqueava qualquer envio de confirmação de leitura ao remetente — inclusive chamadas manuais via API que retornavam "success" sem efeito real.

Solução: habilitado via POST /settings/set/lucenadecoracoes:

  • readMessages: true — Evolution API chama sock.readMessages() automaticamente ao receber cada mensagem
  • readStatus: true — Evolution API envia o receipt de leitura ao remetente via protocolo WhatsApp Web (Baileys)

Comportamento atual: o ✓✓ azul aparece no WhatsApp do cliente assim que a mensagem chega ao servidor do bot — antes mesmo do processamento pela IA. Isso é o comportamento correto para bots de atendimento: confirma ao cliente que o sistema recebeu a mensagem.

Nota: este é um ajuste de configuração na Evolution API, não requer código no ComAgente. Em caso de recriação da instância, aplicar novamente via API ou pelo painel da Evolution.

6.22 Mensagens recebidas não apareciam no workspace — fix definitivo — 29/05/2026

Histórico: em 20/04/2026 foi implementada a busca via PostgreSQL da Evolution API para contornar o bug do endpoint HTTP que retornava apenas fromMe: true. Funcionou até ~26/04/2026.

Erro: mensagens dos clientes apareciam no preview da lista de contatos (via chat list HTTP) mas não dentro do chat (via query PostgreSQL). Testes diretos na Evolution API revelaram a causa raiz:

Tipokey.remoteJidkey.remoteJidAlt
Enviada (bot/IA)557182608738@s.whatsapp.net—
Recebida (cliente)211132707020926@lid557182608738@s.whatsapp.net

O WhatsApp moderno usa JID no formato @lid (device-linked ID) como identificador primário para mensagens recebidas. O telefone real fica em remoteJidAlt. A query PostgreSQL buscava apenas por remoteJid, nunca encontrando as mensagens recebidas.

Diagnóstico — testes diretos na Evolution API (29/05/2026):

Query HTTP enviadaResultado
where: { key: { remoteJid: "phone@s.whatsapp.net" } }335 mensagens, todas fromMe: true (enviadas)
where: { key: { remoteJid: "211132707020926@lid" } }183 mensagens, todas fromMe: false (recebidas)
where: { key: { remoteJidAlt: "phone@s.whatsapp.net" } }112 mensagens recebidas ✓

Solução implementada em app/api/evolution/messages/route.ts e lib/evolution/client.ts:

  • Eliminada dependência do PostgreSQL para busca de mensagens (instável)
  • Duas queries HTTP em paralelo via Promise.all:
    1. findMessages(phoneJid) → filtra por remoteJid = @s.whatsapp.net → mensagens enviadas
    2. findReceivedMessages(phoneJid) → filtra por remoteJidAlt = @s.whatsapp.net → mensagens recebidas
  • Merge deduplicado por key.id (WhatsApp message ID)
  • Horário corrigido de America/Bahia para America/Sao_Paulo

Resultado verificado pelo cliente: conversa completa (enviadas + recebidas) aparece no workspace. ✓

Nota para próximas sessões: O PostgreSQL da Evolution API (EVOLUTION_DB_URL) continua ativo para o mapeamento @lid → phone via getLidMapping() (usado no chats route). Mas a rota /api/evolution/messages agora usa exclusivamente o HTTP da Evolution API.

"SELECT \"key\"->>'fromMe', \"key\"->>'remoteJid', \"pushName\", \"messageTimestamp\" \
FROM \"Message\" WHERE \"instanceId\" = '8d9a15b5-e063-4e2d-9900-3f5929c6129a' \
ORDER BY \"messageTimestamp\" DESC LIMIT 5;"

swapon /swapfile

caches.keys().then(keys => keys.forEach(key => caches.delete(key)))

powershell -Command "Remove-Item -Recurse -Force '.git\rebase-merge'"
